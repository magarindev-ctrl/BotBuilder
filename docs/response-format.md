# LLM 응답 형식

## JSON 응답 형식과 잔여물 제거

- 새 응답의 `schemaVersion`은 숫자 `2`, `task`는 선택한 작업 ID, `data`는 작업별 허용 필드만 사용하도록 안내합니다. OOC 제목·코드 펜스·JSON 밖 설명을 금지하고, 대화·Markdown·코드는 해당 문자열 값 안에 넣도록 지시합니다.
- 설계 대화는 `reply`와 빈 `changes: []`를 기본으로 합니다. 대화만 하는 예시와 명시적으로 수정안을 만드는 예시를 분리하고, 다른 작업에도 해당 JSON 예시를 제공합니다. **프롬프트 → JSON 응답 형식과 예시**에서 확인할 수 있습니다.
- 출력 형식은 기존 `<<OUTPUT_FORMAT>>` 자리로 전달하므로 저장한 사용자 템플릿에도 새 예시가 반영됩니다. 사용자 템플릿과 프리셋의 프리필을 자동으로 덮어쓰지 않습니다. 시스템 기본 문안까지 갱신하려면 해당 작업의 **기본값으로 초기화**를 사용하세요.
- 응답에 `## OOC Response`, Markdown 코드 펜스, 앞뒤 설명이 붙으면 완성된 JSON 객체를 찾아 스키마 검증 후 사용합니다. 문자열 안의 따옴표·역슬래시·중괄호를 구분하므로 원고 안의 Markdown·HTML·Lua·JSON 예시는 보존합니다. 성공한 응답의 바깥 잔여물은 대화나 수정안에 넣지 않습니다.
- JSON 내부 문법·필드·작업 종류·참조는 계속 검증합니다. 유효한 응답이 여러 개면 임의로 고르지 않으며, 배열이나 중첩 포장 안의 객체를 임의로 꺼내지 않습니다. 손상된 JSON을 자동 수리하지 않고 기존 1MiB 응답 상한을 유지합니다. 제안은 기존처럼 사용자가 검토하고 적용합니다.

비어 있는 외부 필드(null·빈 문자열·빈 배열·빈 객체)는 버리고 나머지를 검증합니다. 예를 들어 설계 대화 응답의 `"choices": []`는 무시됩니다. 내용이 있는 외부 필드는 `허용하지 않는 필드` 오류로 거부합니다.

응답이 중간에 끊겨 JSON이 닫히지 않은 채 끝나면 `응답이 중간에 끊겼습니다 · N자 수신`으로 표시합니다. 리스의 최대 응답 토큰은 그대로 모델에 전달되므로, 그 값 아래에서 끊겼다면 모델·중계 서비스의 출력 상한이거나 스트리밍 중 연결이 끊긴 것(모바일 화면 꺼짐·앱 전환)입니다. 잘린 응답은 복구하지 않으며, 요청을 탭별로 나누거나 부분편집으로 다시 요청해야 합니다. 기본 프롬프트는 기존 원문이 있는 긴 본문을 부분편집으로만 보내고 새로 쓰는 긴 본문은 한 응답에 하나만 넣도록 지시합니다.

## 원문 블록

이스케이프가 많이 필요한 값(Lua, HTML, CSS, 정규식, 긴 본문)은 JSON 문자열 대신 **원문 블록**으로 보낼 수 있습니다. JSON 안의 그 자리에는 `{"block":"이름"}`을 쓰고, JSON 객체가 끝난 뒤 새 줄에 `<<<이름>>>` 한 줄, 원문 그대로, `<<</이름>>>` 한 줄을 씁니다. 블록 안은 이스케이프하지 않습니다.

```
{"schemaVersion":2,"task":"lua","data":{"scripts":[{"ref":null,"comment":"시작","code":{"block":"lua1"}}],"removeScripts":[],"variables":{},"removeVariables":[]}}
<<<lua1>>>
function onStart(accessKey)
  setChatVar(accessKey, "day", "1")
end
<<</lua1>>>
```

- 이름은 영문·숫자·`_`·`.`·`-` 1~40자이며 응답 안에서 유일해야 합니다. 여는 줄과 닫는 줄은 줄 첫머리에서 시작해야 합니다.
- 모든 문자열 필드(code, text, content, comment, before, after, 변수 값, plan의 instruction 등)에 쓸 수 있습니다. 짧은 값은 지금처럼 문자열로 써도 됩니다.
- 봇빌더는 블록을 먼저 잘라낸 뒤 JSON을 읽고, 참조 자리에 블록 내용을 끼워 넣은 다음 지금과 같은 검증을 합니다. 블록 안의 중괄호·따옴표는 JSON 파서에 닿지 않습니다.
- 닫히지 않은 블록은 끊긴 응답으로 처리합니다. JSON이 참조하지 않는 블록, 없는 블록을 가리키는 참조, 중복 이름은 오류입니다.

## JSON 문법 오류 안내

응답이 끝까지 왔지만 JSON 문법이 깨져 있으면 `응답의 JSON 문법이 깨졌습니다 · N자 부근 "…앞뒤 원문…"`으로 깨진 위치를 보여 줍니다. 봇빌더는 그 위치를 담은 지시를 붙여 한 번 자동으로 다시 요청하고, 두 번째도 실패하면 오류를 남깁니다. 깨진 JSON을 고쳐서 쓰지는 않습니다.

## 분할 작업과 `plan` 필드

응답 객체는 `schemaVersion`, `task`, `data` 외에 선택 필드 `plan`을 가질 수 있습니다. `plan`은 아직 쓰지 않은 남은 구간의 배열이며 각 항목은 `{"title": "구간 이름", "instruction": "그 구간에서 작성할 내용과 위치"}`입니다(제목 120자, 지시 2,000자 이하, 전체 최대 12개). 계획만 세우고 아직 아무것도 쓰지 않을 때는 `data`를 `null`로 둘 수 있으며, 이때는 `plan`이 반드시 있어야 합니다.

봇빌더는 `plan`을 받으면 첫 구간의 `data`를 임시 원고에 적용한 뒤, 사용자 요청에 `[분할 작업 k/N] 이번 구간: 제목`과 지시를 덧붙여 다음 구간을 요청합니다. 그때의 현재안은 이전 구간이 반영된 임시 원고이므로 로어북 ref와 부분편집의 before는 그 현재안 기준입니다. 각 구간 응답은 남은 구간만 다시 `plan`에 적고, 마지막 구간은 `plan`을 생략합니다. 설정에서 분할 작업을 끄면 출력 계약이 plan을 금지하고, 그래도 오면 따라가지 않습니다.

## Lua 변수 값

리스의 초기 변수는 `key=value` 한 줄 목록이므로 `variables`의 각 값은 **한 줄 문자열**입니다. 숫자도 `"0"`처럼 문자열로 쓰고, 값에 등호와 줄바꿈은 넣을 수 없습니다. 객체·배열·숫자가 오면 "변수 X: 값은 한 줄 문자열이어야 합니다"로 거부합니다. 슬롯·목록처럼 구조화된 값은 `partner1_name`, `partner1_state`처럼 변수를 나눕니다. 기존 변수 값은 다른 문자열 필드와 같이 `{"edits": [...]}` 부분편집으로 고칠 수 있습니다.

## 공통 텍스트 부분편집

엄격한 원문 매칭에 더해, 설명·첫 메시지·시작 상황 본문과 로어북 content/comment 같은 일반 문장 필드에서는 원문이 정확히 일치하지 않거나 여러 곳에 일치할 때 후보 선택·원문 직접 선택·교체 내용 편집·건너뛰기를 제공합니다. 후보는 자동 적용하지 않으며 최종 반영은 수정안 적용 버튼으로 합니다. 코드·정규식·로어북 키·변수의 구간 수정은 엄격한 매칭만 사용합니다.

기존 원고의 텍스트 수정에는 완성 문자열 대신 다음 값을 사용할 수 있습니다. 예를 들어 기존 CSS에서 색상 선언 한 곳만 바꿉니다.

```json
{
  "schemaVersion": 2,
  "task": "regex",
  "data": {
    "upsert": [{
      "ref": "r0",
      "rule": {
        "out": { "edits": [{ "before": "color: #fff;", "after": "color: #ddd;" }] }
      }
    }],
    "remove": []
  }
}
```

- 적용 대상: 설명·첫 메시지·시작 상황의 text, 로어북 comment/key/secondkey/content, 정규식 comment/in/out, Lua comment/code, 기존 초기 변수의 각 값. 설계 대화의 changes에도 같은 형식을 사용합니다.
- before는 비어 있지 않은 원문이며 공백·줄바꿈까지 정확히 한 곳에 일치해야 합니다. 여러 곳에 일치하면 주변 문맥을 더 포함해야 합니다. 정규식 치환이나 유사 매칭은 하지 않습니다.
- 한 필드의 edits는 1~100개입니다. 모든 구간을 요청 당시 원문에서 찾고, 겹침·불일치·중복이 하나라도 있으면 제안 전체를 거부합니다. 앞 수정의 결과를 다음 before로 사용하지 않습니다.
- 삽입은 기존 문맥을 before로, 문맥과 추가 내용을 after로 지정합니다. 삭제는 빈 after 문자열을 사용합니다. 줄 번호는 적용 위치가 아닌 검토용 표시입니다.
- 검토 화면은 변경 구간·필드와 기존/수정 후 줄 번호를 보여 줍니다. Lua·CSS를 실행하거나 언어 문법을 완전히 검사하는 기능은 아닙니다. 원고가 바뀐 뒤의 오래된 제안도 기존처럼 거부합니다.
- 새 항목과 빈 필드의 첫 작성, 명시적인 전체 재작성은 기존 완성 문자열 형식을 사용합니다. 기존 Lua는 ref와 code 또는 comment만 보내면 생략한 값은 보존됩니다. 새 Lua는 ref:null, comment, code가 모두 필요합니다. 설정값(type/mode/flag/불리언/숫자), 대화 reply와 choices 안내 정보는 기존 형식을 사용합니다.
- 자동·수동 저장에는 완성 코드로 확장하지 않은 수정안을 보관합니다. 적용 시 다시 검증합니다. 실제 변경이 없는 응답은 적용할 제안을 만들지 않습니다. 실패한 부분편집을 자동으로 전체 교체하거나 재요청하지 않습니다.
- 저장본 외곽의 schemaVersion은 1로 유지합니다. LLM 응답은 2를 안내하며 기존 버전 1의 완성 문자열 응답·저장된 제안도 계속 읽습니다. 부분편집을 버전 1로 보내면 거부합니다. 버전 2 수정안을 포함한 저장본은 이전 BB 버전으로의 복원을 보장하지 않습니다.
- 저장한 사용자 프롬프트는 유지합니다. 새 출력 계약과 작업별 부분편집 예시는 기존 OUTPUT_FORMAT 자리에 전달됩니다. 출력 토큰 절감은 모델이 구간 수정 형식을 따를 때 발생하며, 판단에 필요한 원문 입력을 자동으로 줄이는 기능은 아닙니다.
