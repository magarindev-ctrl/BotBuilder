# 1.2.0 이후 작업 메모 · LLM 소통 규약 효율화

작성일 2026-11-02. 브랜치 `claude/botbuilder-1-0-0-improvements-tz0vzh`, 1.2.0 빌드 기준(자동 검증 197개, 브라우저 검증 27개). PC에서 이어서 작업할 때 읽는 문서입니다.

## 1. 1.2.0에 들어간 것

- 로어북 폴더(리스와 같은 구조: 폴더 항목 `mode: 'folder'`, 안의 항목은 폴더 키를 `folder`에 보관), 폴더 단위 이번 요청 포함·리스에서 활성화·항상 활성화.
- 목록 ↔ 본문 분할선(끌기·←/→·더블클릭 초기화, 설정 `listNavWidth`), 목록 접기(설정 `collapsedLists`), 모듈 카드·전송 내용 카드 접기.
- 스트리밍 응답을 조각마다 전체 길이를 다시 재던 O(n²) 처리 제거(`responseText`). 결과 그리기 실패 시에도 작업 표시 해제.
- 사용자 메시지 템플릿을 캐시 친화적 순서로 변경(아래 3절).

## 2. 현재 규약 진단

측정값(`composeMessages`, 한국어 2.2자 ≈ 1토큰 가정):

| 상황 | 글자 수 | 대략 토큰 |
|---|---|---|
| 빈 원고, 로어북 요청 1회(고정 오버헤드) | 12,200 | 5,000~6,000 |
| 로어북 40개(각 600자) + 대화 10턴, 요청 1회 | 39,200 | 17,000~18,000 |
| 위 상황에서 분할 작업 4구간 | ×4 | 70,000 안팎 |

유지할 것:
- 응답 검증 → ref 병합 → 사용자 검토 후 적용. `runLLMModel`은 텍스트만 주고받으므로 도구 호출·JSON 모드는 쓸 수 없고, 어떤 형태든 텍스트 규약과 플러그인 쪽 파서가 필요하다.
- 원문 블록(`<<<이름>>>`)과 분할 작업은 JSON의 약점(이스케이프, 출력 상한)을 실제로 메웠다.

비효율:
1. 입력 반복. 요청마다 시스템 프롬프트, 출력 규약·예시, 현재 원고 전체, 대화 전체를 다시 보낸다. 분할 작업은 구간마다 임시 원고를 또 보낸다. 실제로 바꾸려는 내용은 수백 토큰인데 요청 한 번이 2만 토큰에 가깝다.
2. 캐시가 안 걸리는 순서(1.2.0에서 해결, 클로드는 미해결 · 3절).
3. 전부 아니면 전무. JSON 한 글자가 어긋나면 응답 전체를 버리고 재요청한다. 1.1.5~1.1.10의 수정이 모두 이 종류였다. before/after 부분편집도 원문을 글자 그대로 옮겨야 성립한다.
4. JSON 포장 자체는 출력의 1~2할. 코드·긴 본문 이스케이프가 그 이상이었으나 원문 블록으로 많이 줄었다.

## 3. 적용 완료 · 템플릿 순서(1.2.0)

- `src/core.js` `USER_TEMPLATE`: 작업 종류 → 현재안 → 참고자료 → 출력 형식 → 설계 대화 기록(`<<CONVERSATION>>`) → 미적용 제안(`<<PENDING_PROPOSALS>>`) → 사용자 요청사항. 같은 원고로 이어지는 요청은 대화 기록 앞까지 글자 그대로 같다(테스트로 보장).
- `LEGACY_USER_TEMPLATE`(이전 순서)로 저장된 프롬프트는 `ui.js` 초기화에서 새 순서로 갱신해 저장하고, 직접 편집한 템플릿은 그대로 둔다. 새 자리가 없는 템플릿은 대화·제안을 참고자료 안에 넣어 보낸다(호환).
- 효과 범위: OpenAI 자동 캐시, Gemini 암시적 캐시처럼 앞부분이 같으면 알아서 캐시하는 제공자.
- **클로드 한계**: 리스바드는 메시지의 `cachePoint`가 있을 때만 `cache_control`을 붙이고(`src/ts/process/request/anthropic.ts`), 같은 역할의 연속 메시지를 한 덩어리로 합친다(`request.ts`의 formated 병합, 문자열을 `'\n'`으로 이어 붙임). 플러그인이 보내는 사용자 메시지 하나에 요청문이 섞여 있으면 블록 해시가 매번 달라져 캐시가 걸리지 않는다. 해결은 7절 C.

## 4. 조사 결과

| 후보 | 방식 | 장점 | 단점 · 근거 |
|---|---|---|---|
| 현재: JSON 봉투 + 블록 + before/after | 메타데이터·본문을 JSON에, 긴 본문은 블록 | 검증·병합 확실, 안정화됨 | 한 글자 어긋나면 전체 폐기. 형식 제약이 추론 품질을 떨어뜨린다는 연구(Let Me Speak Freely, EMNLP 2024) |
| 태그 전면화(XML/`<<<블록>>>`) | 본문은 태그 블록, JSON은 ref·계획만 | 이스케이프 실패 거의 소멸. 클로드는 XML 태그 구조에 익숙(Anthropic 공식 안내). 블록 단위로 살릴 수 있음 | 중첩·타입 검증은 직접 구현 |

| 통합 diff / V4A | 줄 문맥으로 위치 지정 | GPT-4 Turbo 게으른 출력 완화 사례 | 산문에 부적합, 2026 소규모 비교에서 형식 실패 최다 |

## 5. 결정

- 검색/치환(before/after)은 **유지**. 새로 도입할 것 없음. before를 짧고 유일하게 잡으라는 지시만 보강.
- 태그 전면화는 **블록 기본화**로 도입. 순수 XML 전환은 하지 않는다(중첩 구조 검증을 새로 짜야 하고 테스트 대부분이 바뀌며 이득은 블록 기본화와 같다).
- 그 위에 **블록 단위 살리기**를 올린다.
- JSON은 버리지 않는다. task, ref, plan, 설정값만 남긴 얇은 봉투로 쓴다.

## 7. 할 일

### A. 블록 기본화 (작음 · 1.2.x)
- [ ] `src/core.js` `jsonContract`: "설명·첫 메시지·로어북 content·정규식 out·Lua code·before/after는 **기본적으로** 블록으로 보내라. JSON에는 ref·comment·key·설정값·plan만 둔다. 짧은 값(한 줄, 80자 이하)은 문자열로 써도 된다"로 문구 변경. 예시도 블록 기본으로 교체(`responseExamples`, `formatFor`의 patchGuide·loreDeltaExample).
- [ ] `docs/response-format.md`·`docs/guide.md` 출력 규칙 갱신. `THIRD_PARTY_NOTICES.txt` Modified 줄, `CHANGELOG.md`.
- [ ] 테스트: 블록 기본 예시가 `parseResponse`를 통과하는지, 문자열 인라인도 여전히 받는지, 프롬프트에 새 문구가 있는지(`tests/core.test.mjs`, `tests/blocks.test.mjs`).
- [ ] 파서는 변경 없음(`extractBlocks`, `resolveBlocks`, `applyBlocks` 그대로). 블록 이름 규칙(영문·숫자·_)과 닫는 태그 허용 범위(1.1.10) 유지.
- 완료 기준: 모의 응답 전체를 블록 기본으로 바꿔도 189+개 기존 테스트가 통과하고, JSON 부분이 수백 자 이내.

### B. 블록 단위 살리기 (중간 · 1.3.0)
- [ ] `parseResponse`/`applyBlocks`: 참조한 블록이 없거나 블록이 잘린 경우 전체를 버리지 않고, 해당 항목(lorebook upsert 한 개, scripts 한 개, edits 한 개)만 `missing`으로 표시해 나머지를 반환. 끊김(`TruncatedResponseError`)은 "마지막 항목부터 결손"으로 분류.
- [ ] `ui.js` `receive`/`absorb`: 결손 항목이 있으면 검토 카드에 "빠진 항목 N개" 표시, 메시지에 노트. 재요청은 **반드시 `confirmRetry`로 사용자에게 목적·여부 확인**(1.1.8 규칙 유지) 후 빠진 항목만 요청하는 stepText 구성.
- [ ] 분할 작업과의 상호작용: 결손 재요청은 구간 수(`chunkMax`)에 포함.
- [ ] 테스트: 5개 중 1개 블록 누락 → 4개 카드 + 결손 1개, 재요청 거절 시 4개만 남음, 승인 시 합쳐짐. `tools/verify-browser.mjs`에 한 장면 추가.
- 완료 기준: 블록 하나가 빠진 응답에서 원고 적용 가능한 카드가 만들어지고 재요청은 사용자 확인 뒤에만 발생.

### C. 클로드 캐시 (작음~중간 · 1.3.x)
- [ ] `composeMessages`가 메시지 세 개를 돌려주도록 선택지 추가: `system`(규약), `user`(현재안·참고자료·출력 형식, `cachePoint: true`), `user`(대화·제안·요청). 리스바드는 연속 user를 합치므로 **첫 번째 안정 부분을 system 역할로** 보내는 쪽이 실제로 캐시된다. system 메시지 둘(규약 + 안정 자료)에 `cachePoint`를 두는 구성으로 확인 필요(`anthropic.ts`의 system 처리 경로).
- [ ] 프리셋 모드(`assemblePreset`)는 cache 블록이 이미 `cachePoint`를 다루므로 직접 모드만 대상.
- [ ] 실제 리스바드에서 `cache_read_input_tokens`가 0이 아닌지 확인(모의 테스트로는 확인 불가 · 정적/실환경 구분해 기록).
- [ ] 설정 토글은 두지 않는다(캐시 지점은 비용을 늘리지 않음). 단, 1시간 캐시는 리스바드 설정(`claude1HourCaching`)을 따른다.

### D. 입력 줄이기 (중간)
- [ ] 대화 기록 상한: 최근 N턴(기본 12) 또는 글자 상한, 설정에서 조절. 넘치는 앞부분은 "이전 대화 요약은 제공하지 않음" 한 줄로 대체.
- [ ] 설계 대화(workshop)에서 "원고 전체 대신 제작 노트·필드 길이 요약만 보내기" 선택지(요청 설정의 체크). 요약은 필드명과 글자 수, 로어북은 이름·키워드 색인만.
- [ ] 분할 작업: 구간마다 임시 원고 전체 대신 "이번 구간이 다루는 필드 + 계획 + 직전 구간 결과 요약"만 보내기. `previewRequest(override.session)` 경로에서 `contextOf`를 작업·구간별로 좁힌다.
- [ ] 테스트: 전송 글자 수가 기준 시나리오(2절 표)에서 얼마나 줄었는지 숫자로 기록해 `docs/verification.md`에 남김.

### E. 로어북 색인 표 형식 시험 (선택)
- [ ] 로어북 항목의 comment·key·insertorder·alwaysActive만 TOON/CSV 식 표로, content는 블록으로 보내는 실험. 모의 테스트로 토큰 절감률 측정 후 채택 여부 결정. 본문까지 표로 바꾸지 않는다.

## 8. 작업 규칙(기존 그대로)

- 자동 재요청은 어떤 경우에도 `confirmRetry`로 목적·여부를 먼저 묻는다(1.1.8).
- `agent.md`: 요청 범위 밖 기능 추가 금지, 구체적 커밋 메시지, 정적 검증과 실환경 확인을 구분해 보고.
- 검증 절차: `npm test` → `node tools/build.mjs` → `WORKSHOP_BROWSER=<크롬 경로> node tools/verify-browser.mjs`(결과 `verification/browser-results.json`, 스크린샷 `artifacts/`). CI는 dist 재빌드 차이가 없어야 통과하므로 `dist/`를 함께 커밋한다.
- 버전: `package.json`의 version과 `src/core.js`의 `VERSION`을 함께 올리고, `THIRD_PARTY_NOTICES.txt` 맨 위에 Modified 줄, `CHANGELOG.md`·`docs/verification.md` 갱신.
- 릴리즈: 이 세션에서는 태그·Release 생성이 막혀 있어 수동으로 만든다. 본문 초안은 커밋 메시지와 CHANGELOG 항목으로 작성.
